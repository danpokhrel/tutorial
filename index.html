The Tools We Will Use

Dear ImGui

Dear ImGui is a bloat-free immediate-mode GUI library. In immediate mode, the UI is re-built every frame from scratch — there is no retained widget tree. This makes it exceptionally fast to iterate on and ideal for developer tools, editors, and real-time applications.

dear-imgui-rs

dear-imgui-rs is a modern Rust bindings ecosystem for Dear ImGui, created by Latias94. It provides safe, idiomatic Rust wrappers over the C API and ships with:

  • Full docking support — dockspaces, tab bars, and (experimentally) multi-viewport
  • Multiple backends — WGPU, OpenGL (glow), Vulkan (Ash), Winit, SDL3
  • Rich extensions — ImPlot (2D/3D plotting), ImGuizmo (3D gizmos), ImNodes & imgui-node-editor (node editors), file browser, and reflection-based UI
  • Idiomatic Rust API — RAII tokens for scoped operations, strongly-typed flags/enums, and safe lifetimes

dear-app

dear-app is the application runner for dear-imgui-rs. It bundles Winit + WGPU setup into a tiny API so you can focus on your UI instead of window and GPU boilerplate. It provides:

  • run_simple / AppBuilder — a per-frame closure API; AppBuilder adds config, docking, themes, and lifecycle hooks
  • RunnerCallbacks / AppBuilder hooks — optional lifecycle callbacks (on_setup, on_style, on_fonts, on_gpu_init, on_event, on_exit)
  • Add-on initialization — ImPlot, ImNodes, and ImPlot3D presence flags compiled in and enabled via AddOnsConfig::auto()
  • Optional GPU-init and event callbacks — for advanced use such as managing GPU resources or raw input
ℹ️
Why dear-app instead of raw backends?

The dear-imgui-rs ecosystem lets you wire up Winit + WGPU manually, but that's ~100 lines of boilerplate before you draw a single widget. dear-app hides that while preserving escape hatches when you need full control. This mirrors the Rust Book's philosophy: start simple, then reach for lower-level tools when you need them (see Ch. 14.3 on workspaces).

What is dear-imgui-rs?

Before writing code, let's understand the crates we're using and why they exist alongside other ImGui Rust bindings.

The Dear ImGui Ecosystem

Dear ImGui is a C++ library. To use it from Rust, we need bindings that cross the FFI boundary safely. The dear-imgui-rs ecosystem takes a layered approach:

┌──────────────────────────────────────────────┐
│           Your Rust Application               │
├──────────────────────────────────────────────┤
│  dear-app (run_simple / AppBuilder)           │  ← What you write against
├──────────┬──────────┬────────────────────────┤
│dear-im-  │dear-im-  │dear-node-editor         │  ← Extension bindings
│nodes     │plot      │(imgui-node-editor)      │
├──────────┴──────────┴────────────────────────┤
│  dear-imgui-rs  (safe Rust API)               │  ← Core bindings
├──────────────────────────────────────────────┤
│  dear-imgui-sys  (unsafe FFI via cimgui)      │  ← C ABI boundary
├──────────────────────────────────────────────┤
│  dear-imgui-wgpu / dear-imgui-winit           │  ← Platform + renderer
├──────────────────────────────────────────────┤
│  Dear ImGui (C++ docking branch)              │  ← Original library
└──────────────────────────────────────────────┘
Architecture of the dear-imgui-rs ecosystem

Why cimgui?

The ecosystem uses cimgui — a thin C wrapper around the C++ Dear ImGui — as its ABI boundary. This is a deliberate choice explained by the author: generating bindings from the C API provides a stable, portable ABI that works across compilers (especially MSVC), and makes it straightforward to add third-party extensions like ImPlot and ImGuizmo.

📚
Rust Book: Unsafe Rust (Ch. 19)

FFI is an inherently unsafe operation — the Rust compiler cannot verify the correctness of C code. The dear-imgui-sys crate encapsulates all unsafe calls, and dear-imgui-rs builds safe wrappers on top. This is exactly the pattern described in Chapter 19.1: wrap unsafe code behind a safe abstraction.

Key Design Patterns

Understanding these patterns will make the API feel natural:

1. RAII Tokens for Scoped Operations

In C++ ImGui, you call Begin() and must remember End(). In dear-imgui-rs, scoped operations return RAII tokens that call End() when dropped:

RAII pattern
// The _window token calls ui.end_window() when dropped
let _window = ui.window("My Window")
    .size([400.0, 300.0], Condition::FirstUseEver)
    .begin();

ui.text("Content inside the window");
// _window dropped here → end_window() called automatically

Alternatively, the .build() method takes a closure, making the scope explicit:

Builder closure pattern
ui.window("My Window")
    .size([400.0, 300.0], Condition::FirstUseEver)
    .build(|| {
        ui.text("Content inside the window");
    });
📚
Rust Book: RAII & Drop (Ch. 15.3)

RAII (Resource Acquisition Is Initialization) is a Rust-native pattern — Chapter 15.3 covers the Drop trait. The ImGui bindings use it extensively so you can never forget to close a scope.

2. Ui Extension Traits

Extensions like ImNodes are added to the Ui type via extension traits. You import the trait to unlock new methods:

Trait extension pattern
use dear_imnodes::ImNodesExt;

// Importing the trait adds .imnodes_editor() to the Ui
let mut editor = ui.imnodes_editor(&nodes_context, Some(&editor_context));
📚
Rust Book: Traits (Ch. 10.2)

Extension traits follow the pattern from Chapter 10.2. They let external crates add methods to types they don't own — a core Rust idiom for composition.

3. Strongly-Typed IDs

ImNodes uses integer IDs internally, but the Rust bindings wrap them in newtypes (NodeId, PinId, LinkId) so you can't accidentally pass a node ID where a pin ID is expected:

Newtype IDs
// Each ID type is distinct — the compiler catches mix-ups
let node = imnodes::NodeId::new(1);
let pin = imnodes::PinId::new(10);
let link = imnodes::LinkId::new(100);

// editor.node(pin);  // ❌ won't compile — type mismatch
editor.node(node);    // ✅ correct
📚
Rust Book: Newtype Pattern (Ch. 19.3)

Newtypes are covered in Chapter 19.3. They have zero runtime cost and give you compile-time type safety — a cornerstone of idiomatic Rust.

dear-app: The Application Runner

dear-app sits at the top of the stack and gives you two entry points:

Simple: run_simple / run

For applications that only need persistent UI state — no raw window events, no GPU resources — run_simple takes a per-frame closure (no config). When you need window title, size, or docking configuration, use run, which takes a RunnerConfig, an AddOnsConfig, and a closure that receives (&Ui, &mut AddOns<'_>):

run_simple minimal example
use dear_app::{DearAppError, run_simple};
use dear_imgui_rs::Condition;

fn main() -> Result<(), DearAppError> {
    let mut clicks = 0;
    run_simple(move |ui| {
        ui.window("Hello")
            .size([360.0, 160.0], Condition::FirstUseEver)
            .build(|| {
                if ui.button("Click me") {
                    clicks += 1;
                }
                ui.same_line();
                ui.text(format!("Clicks: {clicks}"));
            });
    })
}

Advanced: AppBuilder / RunnerCallbacks

When you need context initialization, raw window events, GPU resources, device-loss recovery, or deterministic teardown, use the AppBuilder builder pattern with its lifecycle callbacks (also exposed via the RunnerCallbacks struct):

AppBuilder lifecycle hooks
// AppBuilder / RunnerCallbacks lifecycle hooks (0.15.x):
// on_setup    — customize the ImGui Context before first frame (&mut Context)
// on_style    — apply custom ImGui styling
// on_fonts    — configure font atlas
// on_gpu_init — called once after window + GPU are ready
// on_event    — raw Winit window events
// on_exit     — deterministic cleanup
ℹ️
When to use which?

Start with run_simple for prototyping and UI-focused apps. Graduate to AppBuilder when you need: the ImGui Context (e.g. to create ImNodes contexts), custom GPU textures, raw input handling, or production-grade teardown. In this tutorial, we'll start with run and evolve toward a structured AppBuilder architecture.

Why these versions?

Chapter 7 introduces the module system. Key principles: separate concerns into modules (graph data vs UI rendering), use mod.rs or file-based modules to declare module roots, and prefer pub use re-exports to create a clean public API. We follow all three here.

The Separation of Concerns

Our structure separates three concerns:

  • Data model (graph/) — pure Rust structs and enums representing the graph. No ImGui imports here.
  • UI rendering (ui/) — functions that read from the graph model and render ImGui widgets. Mutates graph state in response to user interaction.
  • Application wiring (app.rs, main.rs) — holds the state struct, configures dear-app, and calls into the UI module each frame.
💡
Why separate the data model from the UI?

This separation makes the graph model testable without a GPU or window. You can write unit tests for link validation, ID allocation, and graph operations using pure Rust — exactly as the Rust Book encourages in Chapter 11.1.

Chapter 04

Your First Window

Now let's understand the immediate-mode paradigm and the run API by building a simple interactive window with state.

Understanding Immediate Mode

In a retained-mode GUI (like Qt or GTK), you create widgets once and the framework holds them. In immediate mode, you re-issue all UI commands every frame. The key insight is:

ℹ️
Immediate Mode in One Sentence

Your UI function is called 60+ times per second. Each call describes the current state of the UI. Widgets return their current interaction state (was this button clicked? was this value changed?) as return values.

The run API

run takes three arguments:

  1. RunnerConfig — window title, size, theme, docking, and WGPU configuration
  2. AddOnsConfig — which add-ons (ImPlot, ImNodes, etc.) to enable; use AddOnsConfig::auto() for sensible defaults
  3. A closure |ui, addons| { ... } — called every frame with a &Ui reference and &mut AddOns<'_>

State that needs to persist across frames is captured by the closure via move. The closure owns that state for the lifetime of the application:

src/main.rs — stateful counter
use dear_app::{RunnerConfig, DearAppError, AddOnsConfig, run};
use dear_imgui_rs::Condition;

fn main() -> Result<(), DearAppError> {
    let config = RunnerConfig {
        window_title: "Node Graph Editor".to_owned(),
        window_size: (1280.0, 800.0),
        ..Default::default()
    };

    // State captured by the closure — persists across frames
    let mut counter = 0;
    let mut show_hello = true;

    run(config, AddOnsConfig::auto(), move |ui, _addons| {
        ui.window("Hello")
            .opened(&mut show_hello)
            .size([360.0, 180.0], Condition::FirstUseEver)
            .build(|| {
                ui.text("Hello, world!");
                if ui.button("Click me") {
                    counter += 1;
                }
                ui.same_line();
                ui.text(format!("Counter: {counter}"));
            });
    })
}

Notice the patterns:

  • Condition::FirstUseEver — the size/position is only applied the first time the window appears. After that, the user can resize/move it freely.
  • .opened(&mut show_hello) — creates a close button on the window. When clicked, ImGui sets show_hello to false.
  • ui.button("Click me") returns true only on the frame the button is clicked — not every frame it's held.
  • ui.same_line() places the next widget on the same line as the previous one.

Condition Flags

The Condition enum controls when a size/position value is applied:

Condition variants
// Applied only the first time the window appears
Condition::FirstUseEver   // ← most common in practice

// Applied every frame (forces the size/position)
Condition::Always

// Applied exactly once and never again (no first-use tracking, no repeat)
Condition::Once
💡
When to use Condition::Always vs FirstUseEver

Use FirstUseEver for windows the user should be able to resize and move. Use Always for fixed panels (like a toolbar or status bar) where you want to programmatically control the position every frame.

Chapter 05

Application Architecture

The closure-based run works for prototypes, but production applications need a structured state owner. Let's refactor into a proper module hierarchy.

Why Move Beyond a Single Closure?

As our editor grows, putting everything in one move closure creates problems:

  • Untestable logic — graph operations are tangled with ImGui calls
  • Mental overhead — hundreds of lines in one closure
  • No separation — data model, UI, and app wiring are all mixed

The Rust Book's Chapter 7 directly addresses this: "As your project grows, you'll want to organize your code into modules."

Defining the Graph Data Model

Let's start with the pure data model — no ImGui, no rendering, just structs:

src/graph/model.rs
use serde::{Deserialize, Serialize};

#[derive(Debug, Clone, Copy, PartialEq, Eq, Hash, Serialize, Deserialize)]
pub struct NodeId(pub i32);
// PinId and LinkId follow the same pattern (also i32 newtypes).

#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize, Deserialize)]
pub enum PinKind { Input, Output }

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct Node {
    pub id: NodeId,
    pub title: String,
    pub pins: Vec,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct Pin { pub id: PinId, pub kind: PinKind, pub label: String }

#[derive(Debug, Clone, Copy, Serialize, Deserialize)]
pub struct Link { pub id: LinkId, pub from: PinId, pub to: PinId }
📚
Rust Book: Structs (Ch. 5) & Enums (Ch. 6)

Our model uses the core Rust building blocks: structs (Ch. 5) for data records and enums (Ch. 6) for variants like PinKind::Input vs PinKind::Output. Deriving Debug, Clone, and Serialize makes them ergonomic and serializable.

Graph State with ID Allocation

The GraphState struct holds the mutable graph and manages ID allocation — a common pattern for editors where entities are created and destroyed at runtime:

src/graph/state.rs
use super::model::{Link, LinkId, Node, NodeId, Pin, PinId, PinKind};

#[derive(Debug, Clone, Default)]
pub struct GraphState {
    pub nodes: Vec,
    pub links: Vec,
    next_node_id: i32,
    next_pin_id: i32,
    next_link_id: i32,
}

impl GraphState {
    pub fn new() -> Self { Self::default() }

    pub fn next_node_id(&mut self) -> NodeId {
        let id = NodeId(self.next_node_id);
        self.next_node_id += 1;
        id
    }
    // next_pin_id() and next_link_id() follow the same pattern.

    pub fn add_node(&mut self, node: Node) { self.nodes.push(node); }

    /// Validates pin directions (from=Output, to=Input) and rejects duplicates.
    pub fn add_link(&mut self, link: Link) -> bool {
        let from_kind = self.nodes.iter().flat_map(|n| &n.pins)
            .find(|p| p.id == link.from).map(|p| &p.kind);
        let to_kind = self.nodes.iter().flat_map(|n| &n.pins)
            .find(|p| p.id == link.to).map(|p| &p.kind);
        match (from_kind, to_kind) {
            (Some(PinKind::Output), Some(PinKind::Input)) => {}
            _ => return false,
        }
        if !self.links.iter().any(|l| l.from == link.from && l.to == link.to) {
            self.links.push(link);
            true
        } else { false }
    }

    // remove_link, remove_links_for_pin, and remove_node follow
    // the same retain-based pattern. remove_node calls
    // remove_links_for_pin for each of the node's pins.
}
💡
This code is 100% testable

Notice: GraphState has zero ImGui dependencies. You can write unit tests for link validation, ID allocation, and node removal without a GPU or window. This is the payoff of separating the data model from the UI.

⚠️
IDs are never recycled

The next_node_id, next_pin_id, and next_link_id counters monotonically increment and never decrease, even when entities are deleted. This is a deliberate simplification: recycling IDs risks use-after-free bugs if stale references linger. For a long-running editor that creates and deletes millions of entities, you'd eventually want a free-list or generational index scheme (e.g. the slotmap crate). For this tutorial, i32 overflow is practically unreachable. Note also that these counters are serialized with GraphState via serde — when you save and reload a graph, the IDs continue from where they left off, but ImNodes' internal ID space restarts. The positions_initialized flag handles re-syncing positions on reload.

⚠️
Binary-only vs library + binary

For a tutorial project like this, pick one approach: either a pure binary (modules declared in main.rs, no lib.rs) or a library + binary (where main.rs does use imgui_tutorial::... to reference the library crate). Don't declare the same modules in both lib.rs and main.rs — that creates two separate module trees and confuses beginners. This tutorial uses the binary-only approach: modules are declared in main.rs, and crate:: paths work identically — there is no lib.rs.

The Application State Struct

Now let's create app.rs — the state owner that run will capture:

src/app.rs
use crate::graph::{GraphState, Node, Pin, PinKind};

pub struct App {
    pub graph: GraphState,
    pub show_about: bool,
    pub positions_initialized: bool,
}

impl App {
    pub fn new() -> Self {
        let mut graph = GraphState::new();
        let n1 = graph.next_node_id();
        let p1_in = graph.next_pin_id();
        let p1_out = graph.next_pin_id();
        graph.add_node(Node {
            id: n1, title: "Source".to_string(),
            pins: vec![
                Pin { id: p1_in, kind: PinKind::Input, label: "In".into() },
                Pin { id: p1_out, kind: PinKind::Output, label: "Out".into() },
            ],
        });
        // ... seed more nodes as needed ...

        Self { graph, show_about: false, positions_initialized: false }
    }
}

Introducing the Node Editor

Now we bring in dear-imnodes — the node editor extension that turns our blank ImGui window into an interactive canvas for nodes and connections.

What is ImNodes?

ImNodes is a small, dependency-free node editor extension for Dear ImGui. It provides an immediate-mode API for creating nodes with input/output pins, links between them, selection, and a minimap. The dear-imnodes crate provides safe, idiomatic Rust bindings with RAII tokens and strongly-typed IDs.

The key concepts are:

🔲

Editor Canvas

The scrollable, zoomable workspace where nodes live. Created with imnodes_editor().

📦

Nodes

Draggable boxes with title bars. Each has a unique NodeId.

📌

Pins

Input/output endpoints on nodes. Each has a unique PinId and a shape.

🔗

Links

Connections from an output pin to an input pin. Each has a LinkId.

Setting Up the ImNodes Context

ImNodes requires a global Context and per-editor EditorContext objects. With dear-app's imnodes feature, these are managed for you and exposed through the frame context's add-ons. But we can also create them manually for full control:

Creating ImNodes contexts
use dear_imnodes as imnodes;
use dear_imgui_rs::Context;

// The global ImNodes context — tied to the ImGui context
let mut imgui_context = Context::create();

// Create the ImNodes context (must outlive all editor contexts)
let nodes_context = imnodes::Context::create(&imgui_context);

// Create one or more editor contexts (one per independent editor)
let editor_context = nodes_context.create_editor_context();
⚠️
Drop ordering matters

Native ImNodes state is tied to the owning ImGui context. If you store both Context and EditorContext in the same struct, declare the editor context before the ImGui context so it drops first. Otherwise you'll get a use-after-free on shutdown.

In this tutorial dear-app owns the ImGui Context, so our App doesn't store it and this ordering concern doesn't apply yet — but keep it in mind if you ever take ownership of the Context yourself (e.g. for a multi-viewport setup).

        window_size: (1280.0, 800.0),
        docking: DockingConfig { enable: false, ..Default::default() },
        ..Default::default()

    // does NOT compile — see the callout below for why).
    let app: Rc>> = Rc::new(RefCell::new(None));

        .with_config(config)
        .with_addons(AddOnsConfig::auto())

            *app.borrow_mut() = Some(App::new(ctx));
        }})
        // on_frame receives TWO args: (&Ui, &mut AddOns)
        .on_frame({ let app = Rc::clone(&app); move |ui, _addons| {
            if let Some(a) = app.borrow_mut().as_mut() { crate::ui::render(ui, a); }
        }})
        .run()
}
⚠️
Why Rc<RefCell<Option<App>>>?

on_setup and on_frame are separate 'static closures. The naive approach of stashing App in a plain Option<App> shared between both closures does not compile: on_setup needs to borrow the Option to write to it, while on_frame needs to move it — but both closures must be 'static, and a stack local can't satisfy that for both. The fix is interior mutability: wrap the slot in Rc<RefCell<Option<App>>> and give each closure a cloned handle. on_setup writes via borrow_mut(), and on_frame reads via borrow_mut().as_mut(). If your closures need to be Send (e.g., for multi-threaded runtimes), use Arc<Mutex<Option<App>>> instead.

use dear_imgui_rs::Ui;

const RIGHT_PANEL_WIDTH: f32 = 300.0;

pub fn render(ui: &Ui, app: &mut App) {
    crate::ui::toolbar::render_menu_bar(ui, app);

    // Recompute layout every frame from the viewport work area.
    let viewport = ui.main_viewport();
    let work_pos = viewport.work_pos();
    let work_size = viewport.work_size();

    let y0 = work_pos[1];
    let full_w = work_size[0];
    let full_h = work_size[1];

    // Left panel (file tree)
    crate::ui::panels::render_project_panel(
        ui, app, [x0, y0], [LEFT_PANEL_WIDTH, full_h],
    );
    // Right panel (properties inspector)
    crate::ui::panels::render_properties_panel(
        ui, app, [x0 + full_w - RIGHT_PANEL_WIDTH, y0],
        [RIGHT_PANEL_WIDTH, full_h],
    );
    // Central canvas fills the remaining width
    crate::ui::editor::render_editor(
        ui, app,
        [x0 + LEFT_PANEL_WIDTH, y0],
        [full_w - LEFT_PANEL_WIDTH - RIGHT_PANEL_WIDTH, full_h],
    );

Both side panels use NO_TITLE_BAR | NO_RESIZE | NO_MOVE | NO_COLLAPSE flags (not NO_DECORATION, which also removes scrollbars) so they stay pinned and fill the window vertically, while long file trees and pin lists can scroll. 💡
Caching expensive data outside the frame loop

The file tree is a snapshot, not a live view — scanning the filesystem every frame would be wasteful and could stutter on large directories. The tree is built once on first render and only refreshed when the user clicks Refresh. This is the standard pattern for filesystem-backed UI in an immediate-mode context: cache expensive data outside the per-frame loop, and invalidate on user action.

Building Nodes & Pins

Let's populate our canvas with nodes that have title bars, input pins, and output pins — reading directly from our GraphState data model.

The Node Rendering Pattern

Each node is created with editor.node(node_id), which returns a NodeToken (RAII). The token provides methods for rendering the node's content: title bars, input attributes, and output attributes. Each attribute also returns its own RAII token.

Node anatomy
// A single node with a title bar and two pins
let n = editor.node(node_id);

// Title bar — rendered as a header
n.title_bar(|| {
    ui.text("My Node");
});

// Input pin — appears on the left side
{
    let _attr = editor.input_attr(pin_id, imnodes::PinShape::CircleFilled);
    ui.text("In");
    // _attr dropped here → EndAttribute called
}

// Output pin — appears on the right side
{
    let _attr = editor.output_attr(pin_out_id, imnodes::PinShape::QuadFilled);
    ui.text("Out");
    // _attr dropped here → EndAttribute called
}

// n dropped here → EndNode called
💡
Drop vs explicit .end()

Both approaches are valid and compile fine (calling .end() consumes the token, so Drop won't double-call EndNode). Use Drop (let the token fall out of scope) when the node's scope is naturally delimited by a block — as in the example above. Use explicit .end() when you need the node to close at a specific point mid-block, such as inside a for loop where you iterate pins before moving to the next node. The full render_editor code later in this chapter uses n.end() for this reason. Pick one style per codebase and be consistent.

                    PinKind::Output => { /* ... output_attr() with QuadFilled ... */ }

⚠️
ID uniqueness is critical

ImNodes identifies nodes and pins by integer ID. If two nodes share the same ID, or two pins share an ID, the editor will behave unpredictably. Our GraphState allocator ensures uniqueness by incrementing a counter. Never hardcode IDs in rendering code — always use the model's allocated IDs.

Borrowing Challenge: Iterating Nodes

Notice we iterate &app.graph.nodes (immutable borrow). Even though render_editor takes app: &mut App, this is fine: holding &mut App lets you reborrow any single field as shared or mutable, and the borrow checker (via NLL) allows a shared reborrow of app.graph.nodes during the render loop because no conflicting borrow of app.graph is live at the same time. The moment you try to mutate app.graph inside that loop (e.g. adding a link), the mutable reborrow conflicts with the shared one. So we collect the interaction result into a local first, let the shared reborrow end, then mutate:

Borrow pattern for mutation
// 1. Collect interaction data (immutable borrow of app)
let new_link: Option<(_, _)> = {
    let mut editor = ui.imnodes_editor(
        &app.nodes_context,
        Some(&app.editor_context),
    );
    // ... render nodes (borrows &app.graph immutably) ...
    let post = editor.end();
    post.is_link_created().map(|lc| (lc.start_attr, lc.end_attr))
};

// 2. Now mutate app.graph (mutable borrow)
if let Some((start, end)) = new_link {
    let link = crate::graph::Link {
        id: app.graph.next_link_id(),
        from: crate::graph::PinId(start.raw()),
        to: crate::graph::PinId(end.raw()),
    };
    app.graph.add_link(link);
}

Rendering Existing Links

Links are drawn inside the editor frame, before editor.end(). Each link connects an output pin to an input pin:

// Inside the editor frame, after rendering all nodes:
for link in &app.graph.links {
    editor.link(
        imnodes::LinkId::new(link.id.0),

The PostEditor Object

Calling editor.end() returns a PostEditor token. All interaction queries — link creation, link destruction, selection — happen through this object after the editor frame ends:

PostEditor queries
let post = editor.end();

// Was a new link created by drag-connecting pins?
if let Some(link) = post.is_link_created() {
    // link.start_attr and link.end_attr are PinIds
}

// Was a link destroyed (ctrl+click dragged off)?
if let Some(link_id) = post.is_link_destroyed() {
    // link_id is the LinkId of the destroyed link
}

// Was a link dropped (drag started but not connected)?
if let Some(start_attr) = post.is_link_dropped(true) {
    // true = include detached (ctrl+click) drops
}

// Selection queries
let sel_nodes = post.selected_nodes();   // Vec<NodeId>
let sel_links = post.selected_links();   // Vec<LinkId>

// Hovered elements
let hovered_node = post.hovered_node();  // Option<NodeId>
let hovered_link = post.hovered_link();  // Option<LinkId>
let editor_hovered = post.is_editor_hovered(); // bool

// Clear the selection
post.clear_selection();

Handling New Link Creation

When a user drags from one pin to another, ImNodes reports the event through is_link_created(). We need to:

  1. Determine which pin is the output and which is the input
  2. Validate the connection (no duplicates, correct direction)
  3. Create a Link in our GraphState
Link creation handler
// After editor.end(), collect the new link request:
let new_link = post.is_link_created().map(|lc| (lc.start_attr.raw(), lc.end_attr.raw()));

// Then process it (mutable borrow is now safe):
if let Some((a, b)) = new_link && let Some((from, to)) = classify_pins(a, b, &app.graph) {
    app.graph.add_link(Link { id: app.graph.next_link_id(), from, to });
}

/// Determine which pin is an output and which is an input.
/// Returns `Some((output_pin, input_pin))` when valid, or `None`.
fn classify_pins(a: i32, b: i32, graph: &GraphState) -> Option<(PinId, PinId)> {
    let find = |raw: i32| graph.nodes.iter()
        .flat_map(|n| &n.pins).find(|p| p.id.0 == raw);
    match (find(a), find(b)) {
        (Some(pa), Some(pb)) if pa.kind == PinKind::Output && pb.kind == PinKind::Input =>
            Some((pa.id, pb.id)),
        (Some(pa), Some(pb)) if pa.kind == PinKind::Input && pb.kind == PinKind::Output =>
            Some((pb.id, pa.id)),
        _ => None,
    }
}

Using the Theme

Store the theme in App and apply it on the first rendered frame, not in on_setup and not every frame. ImNodes style setters (set_color, set_grid_spacing, etc.) modify the editor context's persistent style state — calling them every frame is wasteful and redundant, and calling them in on_setup is impossible (the setters need a NodeEditor token, which requires a &Ui):

Applying the theme
// In app.rs — store the theme; apply it on the first frame, not in new().
// `imnodes::editor()` requires a &Ui, which isn't available in on_setup.
pub struct App {
    // ... graph, contexts ...
    pub theme: crate::theme::EditorTheme,
    pub theme_applied: bool,
}

// In editor.rs — apply once on the first frame:
pub fn render_editor(ui: &Ui, app: &mut App) {
    ui.window("Node Graph Editor").build(|| {
        let mut editor = ui.imnodes_editor(&app.nodes_context, Some(&app.editor_context));
        if !app.theme_applied {
            app.theme.apply(&editor);  // persistent on the EditorContext
            app.theme_applied = true;
        }
        // ... render nodes and links ...
    });
}
💡
Persistent vs per-frame style

ImNodes style setters write to the EditorContext's persistent state. However, they can only be called on a NodeEditor token, which requires a &Ui — so you can't apply them in App::new() (which only has &mut Context). Apply your theme on the first frame using a theme_applied flag, and leave it alone afterwards. If you ever need to change themes at runtime, apply the new theme in response to a user action, not on every frame.

// In the App struct (add context menu state):
pub struct App {
    // ... existing fields ...
    pub ctx_open_pos: Option<[f32; 2]>,
    pub ctx_hovered_node: Option,
    pub ctx_hovered_link: Option,

    app.ctx_open_pos = Some(ui.io().mouse_pos());
    app.ctx_hovered_link = post.hovered_link().map(|id| LinkId(id.raw()));
    app.ctx_hovered_node = post.hovered_node().map(|id| NodeId(id.raw()));
    ui.open_popup("editor_ctx");
}

// Render the popup — use the stored state, not live hover queries
ui.popup("editor_ctx", || {
    if let Some(link_id) = app.ctx_hovered_link {
        if ui.selectable_config("Delete Link").build() {
            app.graph.remove_link(link_id);
            ui.close_current_popup();
        }
    } else if let Some(node_id) = app.ctx_hovered_node {
        if ui.selectable_config("Delete Node").build() {
            app.graph.remove_node(node_id);
            ui.close_current_popup();
        }
    } else if ui.selectable_config("Add Node").build() {
        // Create a new node with one In/Out pin.
        let id = app.graph.next_node_id();
        let pin_in = app.graph.next_pin_id();
        let pin_out = app.graph.next_pin_id();
        app.graph.add_node(crate::graph::Node {
            id,
            title: format!("Node {}", id.0),
            pins: vec![
                crate::graph::Pin { id: pin_in, kind: crate::graph::PinKind::Input, label: "In".into() },
                crate::graph::Pin { id: pin_out, kind: crate::graph::PinKind::Output, label: "Out".into() },
            ],
        });
        // Defer positioning to the next frame (see callout below).
        app.pending_node_pos = Some((id, app.ctx_open_pos.unwrap_or([0.0, 0.0])));
        ui.close_current_popup();
    }
});
⚠️
Avoid calling ImNodes hover queries inside popups

ImNodes' hover state is associated with the editor canvas, but during popup rendering the "current window" is the popup window. Capture all hover results before opening the popup, store them in App, and reference them inside the popup. This is exactly what the example above does.

⚠️
Positioning a freshly-created node takes one frame

You can't call set_node_pos_screen on a node in the same frame you create it inside the popup: the popup runs after editor.end(), so no NodeEditor token is live, and ImNodes needs a node to exist before it can position it. The fix is the same deferred pattern used elsewhere in immediate mode — stash the target position in app.pending_node_pos and consume it at the top of the next frame's editor block. (Add pub pending_node_pos: Option<(NodeId, [f32; 2])> to App; Chapter 12 moves it into UiState.)

Consuming the pending position next frame
// At the top of render_editor's editor block, before rendering nodes:
if let Some((node_id, pos)) = app.pending_node_pos.take() {
    editor.set_node_pos_screen(to_im_id(node_id), pos);
}

Minimap with Callback

The minimap can report which node the user is hovering. This is useful for showing tooltips or details:

Minimap with hover callback
let mut editor = ui.imnodes_editor(
    &app.nodes_context,
    Some(&app.editor_context),
);

// Collect the hovered node into a Cell — the editor holds an
// immutable borrow of app.nodes_context / app.editor_context,
// so we cannot mutably borrow anything inside the callback.
// Cell> lets the callback write via .set() without
// a mutable borrow (NodeId is Copy).
use std::cell::Cell;
let hovered: Cell> = Cell::new(None);

editor.minimap_with_callback(
    0.25,                                    // size (25% of editor)
    imnodes::MiniMapLocation::BottomRight,   // corner position
    |node_id| {
        hovered.set(Some(NodeId(node_id.raw())));
    },
);

// ... render nodes and links ...

editor.end();

// Now the editor's borrow has ended — safe to write to `app`.
app.minimap_hovered = hovered.get();
⚠️
Why collect into a local?

The editor token holds an immutable borrow of app.nodes_context and app.editor_context. If the callback tried to write app.minimap_hovered directly, you'd have a simultaneous mutable and immutable borrow of app — the borrow checker rejects this. By collecting into a local Option<NodeId> and writing to app only after editor.end() releases the borrow, we satisfy the borrow checker. This collect-then-mutate pattern is essential whenever a callback or iterator borrows part of app while you need to mutate another part.

Loading a Modern Font

By default, dear-imgui-rs falls back to Dear ImGui's ProggyClean bitmap font, which looks pixelated — especially on HiDPI (Retina) displays. The tutorial mentions on_fonts only in a comment and never shows how to use it. Let's fix that.

src/main.rs — font loading
// In AppBuilder, add on_fonts to load a modern TTF:
.on_fonts(|ctx| {
    let font_data = include_bytes!("../assets/Inter-Regular.ttf");
    let mut atlas = ctx.fonts();
    atlas.clear_fonts();  // remove the default ProggyClean
    let cfg = dear_imgui_rs::FontConfig::new()
        .rasterizer_density(2.0);  // crisp on HiDPI
    atlas.add_font_from_memory_ttf(font_data, 18.0, Some(&cfg), None);
})
💡
rasterizer_density for HiDPI

rasterizer_density(2.0) rasterizes glyphs at 2× resolution without changing the on-screen size, so text stays crisp on HiDPI displays. This matters because dear-app calls on_fonts before WinitPlatform::attach_window sets display_framebuffer_scale, so the scale factor is not yet available inside on_fonts. Using rasterizer_density(2.0) is a robust approximation that looks crisp on both 1× and 2× displays without needing to read the scale factor at load time.

Bundle a modern open-source sans-serif (e.g., Inter, OFL) under assets/ in your project. The include_bytes! macro embeds the font at compile time, so no external files are needed at runtime.

Separating UI State from App State

As the tutorial progressed, the App struct accumulated fields from every chapter — graph data, ImNodes contexts, theme, and UI interaction state (context menu position, hovered node/link, demo window toggle, pending actions). This is a common "god object" anti-pattern. For a production architecture, split ephemeral UI interaction state into its own struct:

src/app.rs — with UiState
/// Ephemeral UI interaction state — resets every session.
/// Separated from App so the data model and contexts stay clean.
#[derive(Default)]
pub struct UiState {
    pub show_about: bool,
    pub show_demo: bool,
    pub positions_initialized: bool,
    pub ctx_open_pos: Option<[f32; 2]>,
    pub ctx_hovered_node: Option<NodeId>,
    pub ctx_hovered_link: Option<LinkId>,
    pub minimap_hovered: Option<NodeId>,
    /// Deferred node position (set by the "Add Node" context menu, consumed next frame).
    pub pending_node_pos: Option<(NodeId, [f32; 2])>,
    pub pending: Option<PendingAction>,
}

/// Core application state — graph, contexts, and theme.
/// This is what you test and persist; UiState is ephemeral.
pub struct App {
    pub graph: GraphState,
    pub nodes_context: imnodes::Context,
    pub editor_context: imnodes::EditorContext,
    pub theme: crate::theme::EditorTheme,
    pub ui: UiState,  // UI interaction state, nested
}
💡
Why separate UiState?

The data model (GraphState) and GPU contexts are long-lived and serializable. UI interaction state (which popup is open, what's hovered, pending menu actions) is ephemeral — it resets every session and should not be serialized. Keeping them in separate structs makes the boundary explicit, simplifies serialization (you only save graph, not ctx_open_pos), and makes the code easier to reason about. Access UI state via app.ui.ctx_hovered_node instead of app.ctx_hovered_node.

Final main.rs

Here's how a production main.rs ties everything together:

src/main.rs — production
mod app; mod error; mod graph; mod theme; mod ui;
use app::App; use error::AppError;
use dear_app::{RunnerConfig, DockingConfig, AddOnsConfig, AppBuilder};
use std::cell::RefCell; use std::rc::Rc;
use tracing::info;

fn main() -> Result<(), AppError> {
    tracing_subscriber::fmt()
        .with_env_filter(env!("CARGO_PKG_NAME").to_owned() + "=debug").init();
    info!("Node Graph Editor starting...");

    let config = RunnerConfig {
        window_title: "Node Graph Editor".to_owned(),
        window_size: (1280.0, 800.0),
        docking: DockingConfig { enable: false, ..Default::default() },
        ..Default::default()
    };

    let app: Rc>> = Rc::new(RefCell::new(None));
    AppBuilder::new()
        .with_config(config).with_addons(AddOnsConfig::auto())
        .on_setup({ let app = Rc::clone(&app); move |ctx| {
            *app.borrow_mut() = Some(App::new(ctx));
        }})
        .on_frame({ let app = Rc::clone(&app); move |ui, _addons| {
            if let Some(a) = app.borrow_mut().as_mut() { crate::ui::render(ui, a); }
        }})
        .run().map_err(|e| AppError::Init(e.to_string()))?;
    info!("Shutting down.");
    Ok(())
}

Next Steps

Here are directions to take your node editor further:

  • Shader Graph — Add node types for texture sampling, math operations, and color constants. Our chapter on shader graphs in the imnodes example shows the pattern.
  • Node Templates — Define node types in a registry (enum or trait) so users can instantiate them from a palette. Consider the dear-imgui-reflect crate for reflection-based property editors.
  • Graph Evaluation — Implement topological sort and evaluate the graph to produce output. This is pure Rust logic — no ImGui needed.
  • Custom Node Drawing — Use ImGui draw lists (ui.get_window_draw_list()) to render custom curves, previews, or thumbnails inside nodes.
  • Multiple Editors — Create multiple EditorContext objects for tabbed multi-editor interfaces (as shown in the imnodes example).
  • WASM Deployment — The dear-imgui-rs ecosystem supports WebAssembly. Use dear-imnodes (not dear-node-editor, which is native-only) for the WASM path.
  • imgui-node-editor — For a richer, more feature-full node editor, try dear-node-editor (bindings for thedmd's imgui-node-editor). It supports blueprint-style stack layouts and more advanced interactions.
